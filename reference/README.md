# Reference implementation

Implements the contracts in `../contracts` to demonstrate them and to serve as a test bench. **Not for production**: in-memory stores, development users, no high availability.

| Module | Port | Contract |
| --- | --- | --- |
| `bff` | 8080 | OIDC session with Keycloak, tokens server-side only |
| `authz` | 8082 | `authz.yaml` |
| `telemetry` | 8083 | `telemetry.yaml` |

The BFF forwards the routes in `quadrava.bff.routes` with the user's token (renewed when it expires) and `traceparent`, without the browser's cookies or `Authorization`: `/registry` → a registry that follows `registry.yaml` (`LOWCODE_REGISTRY_URL`, port 8081 if absent: Quadrava CE has none of its own), `/authz` → authorization, `/telemetry` → telemetry, `/api` → the application back end (in development `npm run demo-api` in `frontend/`, port 8084). It protects writes with CSRF (`XSRF-TOKEN` cookie, `X-XSRF-TOKEN` header), answers 401 to API calls without a session and 502 if the service does not respond. After login (`/bff/login?return=...`) it sends the user back only to the origins in `quadrava.bff.frontend-origins`; the root redirects to `quadrava.bff.home` (`LOWCODE_HOME`, normally the runtime). Logout (`POST /logout`) also closes the Keycloak session (OIDC logout with `id_token_hint`); to calls with `Accept: application/json` it responds `{"redirect": "<address>"}` instead of redirecting. Optional tenants (ADR-18): with `quadrava.bff.tenants` (id, label and the users who may use each; none = everybody) the user lists `tenants` and `currentTenant`, `POST /bff/tenant` with `{"tenant": "<id>"}` and the CSRF token switches the session, the last tenant chosen is remembered per user (in memory) for the next login, and the forwarded calls carry `X-Tenant` (one sent by the browser never passes). It also passes `X-Permissions-Version` back to the browser, and event streams (`text/event-stream`, the data sources with `live`, ADR-19) as they arrive, flushing after every read.

Commands: `mvn verify` to build and test everything (checked with JDK 21 and Maven 3.9.6); `mvn -pl authz spring-boot:run` (or `java -jar <module>/target/*.jar`) to start a module (Keycloak must be running: `cd idp && docker compose up`). Tried live on 13 October 2026 with Keycloak 26.8: login, permissions, data, writes with CSRF, logout.

A customer back end must pass the same contract conformance tests as this implementation. The kits are in `frontend/tools` and run with `npm run conformance:registry`, `conformance:authz`, `conformance:telemetry` and `conformance:bff`: over HTTP they check a registry's saving, validation, If-Match, history, publication with ETag, protected environments and review (17 checks); capabilities, permission format, version and batch checks of authorization (11); OTLP payloads, errors and limits of telemetry (6); what the runtime expects from the BFF (`contracts/bff.yaml`: current user, login with return, logout, CSRF; 6 checks without a session, 2 more with the cookies of a signed-in browser and 4 more on the tenants when the user lists them). The reference services pass theirs; authorization and telemetry answer errors in Problem format (RFC 9457). The whole stack starts with `npm run stack` (see the main README).
